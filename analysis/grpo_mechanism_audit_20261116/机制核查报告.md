# 原GRPO机制核查：本地分析结果

> 历史追溯更新：旧task-contract-v2修复包已经覆盖本次35题，未进入当前原1000题GRPO。上轮未先核对历史，现调整“优先再修预算”的唯一主线安排：不从零重写，也不为它单独完整重训。详见[历史复核与实验取舍](../budget_repair_history_20261116/历史复核与实验取舍.md)。本报告数据和反馈缺口事实保持不变。

2026-11-16。本轮仅CPU分析、原生环境动作回放及源码检查，没有加载模型、增加采样、训练或调用外部模型API。未使用旧4192条复评轨迹。

**已定位一个具体反馈缺口：部分明确预算未被解析，超预算购买通过预算门，并在真实后段训练中获得正相对优势。没有找到“这些样本完全没进训练”或“组内优势数值算错”的证据。当前不宜把有限缺口直接扩大成主要瓶颈或显著训练收益，也没有证实token mask错误。**

## 材料、可信度与核查方法

1. 主材料为原在线训练351—500、651—800两窗，SHA256 `01703af869f5fef97e509c0538b0e3c58910b3508b6298b6c2dccd5396416362`。包括10360条生成、600个被实际消费的4轨迹组和300次optimizer_step。按真实optimizer事件确认消费，不用accepted代替。
2. 关联上轮已通过终局及投影汇总校验的CPU恢复筛查记录，不把877条历史不全记录补成确定事实。需求侧使用原1000训练题已有的审核标注和原文证据做保守筛查；不是复用旧checkpoint采样轨迹，也不是全量语义真值。
3. ray_trainer、losses、FSDP engine等使用此次回传的历史绑定源码。项目辅助函数另存固定Git提交 `a583dba` 快照。veRL 0.8的参考实现从uv.lock固定wheel取得，完整SHA256核对为 `4e32830aae80771ee3b5f0d26a2b794d793f3bcece67aff07c2a7c62e948714f`，仅读源码、不安装。该参考包不冒充历史安装文件的独立字节绑定。
4. 用完整轨迹内容指纹对应生成与优化记录。`rollout_index` 会在长度平衡后重新编号，两窗分别有343、380个消费记录序号对应的内容已变化（完全相同记录之间的交换不可辨认），不能按UID+index直接连接。按去除index后的完整记录多重集合核验，两窗各1200条全部对应。早先第一步仅按整组UID确认消费，不受此重编号影响。

可复跑工具：`tools/audit_grpo_mechanism.py`；原生回放：`tools/replay_grpo_mechanism_cases.py`。核心产物为[audit.json](audit.json)、[逐候选优势](flag_advantages.json)、[原生回放及优势](native_case_replays_with_advantages.json)。

## 一、确实存在“预算未进入奖励”的路径

原生链路为：`goal.py` 调用 `explicit_budget_from_instruction` 得到price_upper；`reward.py` 的 `_price_gate` 在其为None时直接返回 `budget_not_declared_v1/pass`。这意味着“不识别这个说法”实际被当作“用户没有声明预算”，而不是保留未知。

原解析器支持部分阿拉伯数字表达，但漏掉“**五十元以内**”“**四百块钱以内**”“**不能超过500元**”“**别超过1600块**”等。另有“低于20元”的严格小于关系；仅补出数字再沿用当前 `<=` 比较仍不足以处理这个边界。

对原1000训练题的保守筛查范围如下：

| 项目 | 数量 |
|---|---:|
| 通过本轮简单预算规则筛查的训练题 | 178 |
| 对应预算条目 | 179 |
| 原解析器返回相同数值上限的条目 | 143 |
| 原解析器返回None的题/条目 | 35 / 35 |
| 数值不同但并非错误 | 1 |

最后1条为6883：同一句有4000以内和3900以内，原解析器取到更严格的3900，不能算漏判。35题列表见[budget_parser_candidates.json](budget_parser_candidates.json)。口语的软硬程度、订单总价/单价仍需在修复验收时逐项确认；此表是限定条件下的候选覆盖，不代表全部1000题有预算的数量，更不能称“所有预算约20%错了”。4060的严格小于在原标注中是range结构，未进入这179条筛查，但已由本次采样公开轨迹确认其边界问题。

### 真实消费案例：22652，高光盘50元以内

原文：`价格的话五十元以内搞定`。选择的公开SKU为暖粉高光加防晒40ml组合，实际确定价75元。原生CPU重放与原日志终局完全一致：

```text
公开需求上限50，已选SKU75
→ goal.price_upper = None
→ 原预算门 budget_not_declared_v1 / pass
→ 终局 partial_alternative_purchase，reward = +0.04375
→ 实际消费组：三个 +0.04375、一个 repeat_loop -0.65
→ 组均值 -0.1296875
→ 三条75元购买的标量优势各为 +0.1734375
→ step755 optimizer_step实际消费
```

同题在参考窗step442也出现两条75元购买被消费、优势为正。这里不需要猜测模型能力：需求和价格公开明确，原反馈确实漏掉约束，原GRPO相对优势又给予较好于同组循环的购买正向信号。

只复制goal并将price_upper设为公开50、保持商品/规格/价格及其他评分不变，原生评分器就把该终局从+0.04375改为wrong_purchase/-0.85。这是终局局部因果核验；没有修改生产奖励或重跑模型，也不表示换奖励后的完整环境进度、候选有效性和训练结果已经得到模拟。

### 对照：不是所有预算错误都缺反馈

| 后段案例 | 公开需求与价格 | 原预算门/终局 | 重建标量优势 |
|---|---|---|---:|
| 22652 / 755 | ≤50，买75 | 预算未声明/pass，partial +0.04375 | +0.1734375 |
| 19271 / 675 | 四百块钱以内，买419 | 预算未声明/pass，partial +0.00078125 | -0.2154296875 |
| 15497 / 659 | 不超过5元，买6 | fail，wrong -0.85 | -1.3875 |
| 5423 / 711 | 1500元以内，买1930 | fail，wrong -0.85 | -0.3741071429 |

五个原生回放案例（以上四个加颜色题373）均与原日志结局匹配。19271虽然漏掉预算硬门，其他偏好和同组比较仍使其优势为负；不能把所有解析漏项说成已被强化。15497、5423已有正确预算惩罚，修解析器不会解释这些剩余错误。本次相机探测20628的120/125元对照也已有正确奖励区分。

已筛到的预算违规，在参考窗为33条、后段为16条；其中分别7、5条来自解析缺失任务。后段真正消费的7条预算违规中，4条优势为负、3条为正；正的3条均是22652。后段1200条消费中，本轮确认的漏解析预算违规为4条，不能据此断言是整体提升有限的主因。

对35题另做原任务标注下的目标商品规格审计：确定性补齐原要求后，35题价格均可解析，均未超过相应公开上限，结果见[budget_target_consistency.json](budget_target_consistency.json)。这降低了修复上限后这些已列目标规格直接变成超预算的担忧，但不证明所有可选规格、任务语义或替代商品均已核验，也不证明所有任务可解。

## 二、样本确实进入优化，暂未找到优势数值错误

| 项目 | 351—500 | 651—800 |
|---|---:|---:|
| 生成组 | 1220 | 1370 |
| 实际消费组 | 300 | 300 |
| 实际消费轨迹 | 1200 | 1200 |
| 更新确认optimizer_updated=1 | 150 | 150 |
| 重建优势极值与日志一致的更新 | 150 | 150 |

配置为GRPO、`norm_adv_by_std_in_grpo=false`、不使用奖励KL；重建 `A_i = R_i - mean(R_group)` 后，每次更新的优势min/max均在1e-6内吻合。每步为两个4轨迹组，真实消费内容和生成多重集合一致；所有300次更新梯度范数有限且大于0，学习率均为1e-6。没有出现能用这些证据确认的全程零梯度、零学习率或简单的组中心化计算错误。

后段有185条“没有成功购买”的轨迹获得正标量优势：168条partial、14条repeat_loop、3条max_steps。**这本身不是算法bug，也不是185条都应被禁止学习。** GRPO做相对比较，-0.65循环可能优于同组-0.85错误购买，partial也可能保留有价值的部分行为。不能把绝对负奖励理解为必然负优势，或把这些条目数解释成梯度占比。

只有当公开硬约束明确违反且奖励没有落实时，才有上节那种更具体的问题。颜色题373也有要求黄色却买其他色的部分购买，在step775获得小幅正优势；但颜色在当前奖励中属于软匹配，这涉及奖励目标设计，不能简单归类为数值实现bug，更不据此恢复全量语义奖励工程。

## 三、训练范围：默认设计是整条生成轨迹，不是只训最后购买

回传训练器在GRPO分支以UID分组，调用outcome advantage并传response_mask；losses按response_mask计算vanilla PPO损失；FSDP engine按loss_mask.sum计算批token数。固定配置为token-mean、1个PPO epoch、entropy_coeff=0、KL loss关闭。

锁定veRL 0.8参考源码进一步明确：

- `tool_agent_loop.py`：模型生成token加入mask=1；工具响应及模板追加token加入mask=0。
- `agent_loop.py`：终局标量reward进入rm_scores；GRPO先沿序列求和取得标量，不是要求reward恰好位于mask=1的最后位置才生效。
- `core_algos.py`：中心化后的标量乘response_mask，广播给该条轨迹所有被训练的生成token。
- `padding.py`：loss_mask取response_mask；token-mean按这些token归一化，不应把原始response_length当作实际学习token数。

所以按默认链路，搜索、选候选、看详情、改规格、购买等生成动作共同承受终局相对优势，工具观察只提供上下文。粗粒度终局信用分配确实存在；**它是方法设计，不是已经定位出的实现错误。** 本轮没有证据证明把训练范围改到最后几步、按长度归一化，或修改某个mask就能提高总成功率。

边界：历史回传没有单独绑定已安装core_algos、父ToolAgentLoop及padding文件，也没有保留当年的逐token mask/advantage/gradient张量。上述参考包全文校验了uv.lock哈希，仍不能冒充云端历史字节证明。因而不能断言当年每个token都正确，更不能声称已从日志证明具体动作的最终参数梯度方向。若以后选择token范围类改进，必须先补该层源码绑定和小型CPU/运行验证；本轮不因此追加模型采样。

## 四、路线决策和下一步

1. **当前分叉方案继续收束。** 本轮没有产生重新启动它的证据，也不把“终局优势粗”直接等同于“应当分叉”。
2. **历史追溯后调整：预算修复已存在，不再从零开发或为它单独完整重训。** 先确定主方法和R0/R1对照条件；若决定迁移修复，再从旧包提取有限预算功能，做原1000题接口/奖励回归，保留歧义且不夹带928划分和私有标注改动。固定轨迹重评分不是新策略训练收益或完整环境反事实。
3. **修复奖励一致性是工程改进，不是新RL算法已经成立。** 35题解析候选和少量已消费误反馈支持修复正确性，不支持承诺几个百分点的Final增益。已正确受罚仍犯错的案例说明，还有策略学习、探索或泛化问题尚未定位。
4. **如后续改奖励，A/B必须共同使用修复后的版本。** 不能同时改奖励和算法，再与旧800作算法归因。旧750/800仍可作历史参照，但新训练起点、匹配对照及是否值得占用1—2轮完整训练预算仍待离线验收；不直接开500/800步训练。

本轮得到的是一个可复现、范围可核查的反馈缺口，以及对若干简单训练故障假设的排除；没有把“发现问题”包装成“已经找到足够强的最终训练方法”。
