# 训练标签签收核对与实际入口接入

日期：2026-11-07。

**新奖励已接入实际GRPO入口并通过CPU连通测试；原1000题的签收登记已生成，但没有全量放行训练。** 没有启动模型推理、GPU训练或调用LLM API。

## 标签签收的结果

输入为 `analysis/semantic_training_revision_20261107/validated1000.jsonl`，与原 `data/grpo/train.jsonl` 的1000个任务一一对应。每道query同时与原冻结商品归档中的原始任务query核对；没有替换模型输入，没有删除任务。

| 状态 | 题数 | 含义 |
|---|---:|---|
| 程序校验通过 | 1000 | 字段、证据来源等程序检查通过，不等于整题语义签收 |
| 有精确整题签收依据 | 7 | 181、313、315、366、390、396、460；签收契约必须与当前契约完全相同 |
| 没有pending，但缺整题签收依据 | 350 | 不能凭缺少报警就宣称已检查了全部遗漏、作用域和需求强弱 |
| 仍有pending记录 | 643 | 包括旧核验能力限制、容差、语义歧义等，需要区分已被全局政策消解的标记和真正未决需求 |
| 必需/偏好仍含uncertain | 217 | 属于上面各状态的重叠统计，不能再与350、643相加 |

**993题未签收，不代表993道题有错，也不是993个新增问题。** 这个数字是当前可执行评分器要求的“整题源需求签收”与历史记录之间的差额。历史的抽样、定向修订和批次程序重放分别保留来源，不能把它们直接写成1000题已逐题整体验证。

`registry1000.jsonl`逐题记录query/契约指纹、签收状态、pending原因及既有抽样/定向审阅来源。本次归并了223道训练题的既有抽样/定向审阅记录；此前覆盖1000题的程序政策重放另存为批次依据，没有把它计成人工逐题审阅。`manifest.json`绑定标签、签收依据、原始query、训练/验证parquet、任务分割、商品归档、训练商品事实、政策和代码依赖。文本指纹仅统一CRLF为LF；二进制文件按原始字节计算SHA256。

已有历史样本验收仍然通过，本次没有重开该环节。商品资料未知按用户已确认A方案处理：固定需求分母、该项不获分，保留真实满足度未知；**源需求本身的强弱或含义未确定，与商品资料未知是两个不同问题**。

## 真实训练入口改动

入口仍为上游 `scripts/train_grpo.py`，新增显式选项：

```text
--evidence-reward-manifest <manifest.json>
--reward-tools-dir <本项目tools目录>
```

未传入时仍使用原Reward v3。启用后：

1. 启动前检查冻结文件、原1000题覆盖、源需求签收、原训练/验证parquet指纹和数据隔离。未通过时在启动veRL之前报错，不静默过滤任务或回退旧奖励。
2. 通过Ray runtime_env把评分工具路径和manifest传到worker；直接用Hydra绕过启动脚本也必须通过签收检查。
3. 实际工具执行后只在内部保留终局的购买ASIN、所选规格及终局/保护事件。不把goal、标准答案或购买记录中的instruction_text送入新评分器或模型消息。
4. 按冻结商品公开资料和同ASIN的已审事实核验实际所选SKU，用新奖励写入`AgentLoopOutput.reward_score`，同时更新`terminal_utility`、`sampling_invalid`、`reward_valid`等组过滤字段。
5. 原生Reward v3结果另存于`shopping.evidence_reward.baseline`；新评分及证据另存于`shopping.evidence_reward.score`。原有`strict/full/native`诊断仍表示旧基准，不能解释为新证据成功率。
6. 验证集采用原v3并标为`validation_native_v3`，不使用训练标签替代验证答案。其成绩与新训练奖励不是同一指标。
7. 保留有执行证据的repeat_loop、max_steps、购买保护耗尽原固定惩罚；基础设施异常和未证实的购买不能产生学习信号。首版不叠加长度塑形。
8. 真正启动时保存`launch_audit.json`及`reward_manifest.json`，包含选用manifest的指纹。

同时修复启动脚本原先在`main()`引用其他函数局部变量`overrides/extra`的问题；现在预检与实际训练使用同一组Hydra参数。

## 验证范围与结果

- 19项新增CPU连通测试全部通过，日志见`integration_tests.log`。
- 79项已有需求/商品/证据奖励回归全部通过，日志见`reward_regression_tests.log`。
- 7道已签收训练题经实际session、动作守卫、工具、AgentLoop结算链路，分数与此前独立静态评分一致。
- 396的脚本化购买回执即使原v3报gold=1，新入口仍按89元超过88元预算输出−0.85；证明新奖励进入实际输出，而非只多写了一份日志。
- 原v3的`reward_unverifiable`不会继续错误屏蔽可用新评分；未签收标签、无购买凭据、非法规格、基础设施错误仍被过滤。
- 通过CLI和直接加载worker后端均核验了未签收时拒绝放行；关闭新奖励时保留原分数；验证任务走原v3。
- 这些测试使用脚本化环境回执和生成桩。本机没有安装veRL/vLLM/torch，**未验证实际Ray集群、真实HTTP环境交互或GPU优化更新**，不能称为已完成小预算GRPO试跑。

## 本地复现（无卡、无API）

在项目根目录执行：

```powershell
.\.venv-llm\Scripts\python.exe .\tools\semantic_training_bundle.py --check .\analysis\semantic_training_signoff_20261107\manifest.json
.\.venv-llm\Scripts\python.exe -m unittest discover -s tools -p test_semantic_training_integration.py -v
```

第一条应报告冻结文件有效、1000题、7题签收、`formal_training_ready=false`。第二条在本机用轻量生成桩测试真实适配代码；不是训练命令。

后续标签签收版本更新后，可用以下命令重新登记，原输入不会被改写：

```powershell
.\.venv-llm\Scripts\python.exe .\tools\semantic_training_bundle.py --output .\analysis\semantic_training_signoff_20261107
```

若整题审阅依据迁移到新的签收账本，使用`--approvals <账本.jsonl>`；账本必须包含与当前契约精确相同的`normalized`及`whole_contract_approved=true`，当前训练标签本身也必须有对应批准标记。不能用更改manifest计数或删除pending代替审阅。
